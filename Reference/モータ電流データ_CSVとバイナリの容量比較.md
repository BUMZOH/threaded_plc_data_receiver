# モータ電流データのCSV保存とバイナリ保存の容量比較
## ― 5000点 × 5桁テキスト と 5000点 × 16bitバイナリの比較 ―

作成日: 2026-08-09

---

## 1. 目的

モータ電流データを長期間保存する場合、CSVのようなテキスト形式で保存する方法と、
16bit整数をバイナリ形式で保存する方法では、必要なデータ容量が大きく異なる。

本資料では、次の条件で容量を比較する。

1. 5000点 × 5桁のテキストデータ（CSV）
2. 5000点 × 1ワード（16bit）のバイナリデータ

今後、モータ電流値をSQLiteのBLOBなどにバイナリ形式で保存する理由を説明するための
技術資料として使用する。

---

# 2. 比較条件

今回は、1つの波形データを5000点とする。

テキスト側は各値が5桁の整数であると仮定する。

例：

```text
12345
23456
34567
45678
...
```

バイナリ側は各値を1ワード、すなわち16bit整数として保存する。

```text
1ワード = 16bit = 2byte
```

したがって、5000点すべてを固定2byteで保存できる。

---

# 3. 5桁テキストデータの容量

ASCIIまたはUTF-8で半角数字を保存する場合、数字1文字は1byteである。

1点が5桁なら、

```text
5文字 × 1byte
= 5byte
```

5000点では、

```text
5000点 × 5byte
= 25,000byte
```

となる。

KiB換算では、

```text
25,000 ÷ 1024
≒ 24.4KiB
```

である。

ただし、これは数値文字列だけの容量であり、
実際のCSVではカンマや改行などの区切り文字も必要になる。

---

# 4. CSVとして保存した場合

## 4.1 1行にカンマ区切りで保存する場合

たとえば、

```csv
12345,23456,34567,45678,...
```

という形式で5000点を保存する。

数値部分は、

```text
5byte × 5000点
= 25,000byte
```

である。

さらに値の間にカンマが必要になる。

厳密には5000点なら区切りカンマは4999個だが、
容量見積もりでは約5000byteとして考えてよい。

```text
数値部分        約25,000byte
カンマ          約 5,000byte
--------------------------------
合計            約30,000byte
```

したがって、

```text
約29.3KiB
```

となる。

---

## 4.2 1点を1行として保存する場合

次のような形式を考える。

```csv
12345
23456
34567
45678
...
```

Windows標準の改行をCRLFとすると、改行コードは2byteである。

1点あたり、

```text
数値  5byte
改行  2byte
-----------
合計  7byte
```

となる。

5000点では、

```text
7byte × 5000点
= 35,000byte
```

つまり、

```text
約34.2KiB
```

となる。

---

# 5. 16bitバイナリデータの容量

16bit整数は、

```text
16bit = 2byte
```

である。

したがって5000点では、

```text
5000点 × 2byte
= 10,000byte
```

となる。

KiB換算では、

```text
10,000 ÷ 1024
≒ 9.8KiB
```

である。

これは値が、

```text
0
100
12345
65535
```

のどれであっても変わらない。

16bit整数として保存する限り、すべて固定2byteである。

---

# 6. 容量比較

5000点のデータを保存した場合の容量を比較すると次のようになる。

| 保存形式 | 5000点あたりの容量 | バイナリ比 |
|---|---:|---:|
| 16bitバイナリ | 約10,000byte（9.8KiB） | 1.0倍 |
| 5桁テキストのみ | 約25,000byte（24.4KiB） | 2.5倍 |
| CSV・カンマ区切り | 約30,000byte（29.3KiB） | 約3.0倍 |
| CSV・1点1行（CRLF） | 約35,000byte（34.2KiB） | 約3.5倍 |

実際のCSVとして考えるなら、

> **16bitバイナリ形式はCSV形式のおよそ1/3程度の容量で保存できる**

と考えてよい。

---

# 7. テキスト形式とバイナリ形式の本質的な違い

## 7.1 テキスト形式

テキスト形式では、数値そのものではなく
「数字を表す文字」を保存する。

たとえば、

```text
12345
```

は5つの文字であるため、

```text
"1" → 1byte
"2" → 1byte
"3" → 1byte
"4" → 1byte
"5" → 1byte
```

合計5byteを使用する。

値の桁数によって容量が変わる。

```text
0       → 1byte
10      → 2byte
100     → 3byte
1000    → 4byte
12345   → 5byte
65535   → 5byte
```

さらにCSVでは、

- カンマ
- 改行
- 必要に応じてヘッダ

なども保存する必要がある。

---

## 7.2 バイナリ形式

16bitバイナリでは、数値を文字列へ変換せず
16bit整数としてそのまま保存する。

```text
0       → 2byte
10      → 2byte
100     → 2byte
1000    → 2byte
12345   → 2byte
65535   → 2byte
```

値の大きさに関係なく固定2byteである。

したがって大量の数値データを保存する用途では、
バイナリ形式は非常に効率がよい。

---

# 8. 1日5000波形保存した場合

1つの波形を5000点とし、
1日に5000波形発生すると仮定する。

## 8.1 16bitバイナリ

1波形：

```text
10,000byte
```

1日：

```text
10,000byte × 5000波形
= 50,000,000byte
≒ 50MB/日
```

---

## 8.2 CSV（カンマ区切り）

1波形を約30,000byteとすると、

```text
30,000byte × 5000波形
= 150,000,000byte
≒ 150MB/日
```

---

## 8.3 1日の比較

```text
16bitバイナリ：約 50MB/日
CSV             ：約150MB/日
```

およそ3倍の差となる。

---

# 9. 1年間保存した場合

365日保存すると仮定する。

## 9.1 16bitバイナリ

```text
50MB × 365日
= 18,250MB
≒ 18.25GB/年
```

## 9.2 CSV

```text
150MB × 365日
= 54,750MB
≒ 54.75GB/年
```

したがって年間差は、

```text
54.75GB - 18.25GB
= 約36.5GB
```

となる。

概算では、

```text
バイナリ：約18GB/年
CSV      ：約55GB/年
差       ：約36GB/年
```

となる。

大量の波形データを何年間も保存する場合、この差は無視できない。

---

# 10. SQLite BLOBとの相性

今回のモータ電流データでは、
1つの波形を1レコードとしてSQLiteへ保存する構成を想定している。

イメージ：

```text
SQLite
┌─────────────────────────────────────┐
│ timestamp                           │
│ machine_no                          │
│ motor_no                            │
│ current_data : BLOB                 │
└─────────────────────────────────────┘
```

`current_data`へ5000点の16bitデータをバイナリとして格納する場合、

```text
1波形 = 約10,000byte
```

となる。

つまり、

```text
1レコード
    └── BLOB
         └── 5000点 × 2byte
             = 10,000byte
```

という非常に分かりやすい構造になる。

---

# 11. PLCデータとの相性

バイナリ形式には、単に容量が小さいだけではなく、
PLCデータとの相性がよいという利点もある。

PLCから受信した16bit整数を考える。

バイナリ形式なら、

```text
PLC
 ↓
16bit整数
 ↓
Python
 ↓
バイナリ化
 ↓
SQLite BLOB
```

という流れになる。

CSVの場合は、

```text
PLC
 ↓
16bit整数
 ↓
Python
 ↓
10進数文字列へ変換
 ↓
カンマ・改行を追加
 ↓
CSV
```

となる。

バイナリ形式では、
数値データを文字列表現へ変換する必要がない。

---

# 12. グラフ表示時の考え方

保存時はバイナリ形式でよいが、
Chart.jsでグラフ表示するときには数値配列へ戻す。

構成は、

```text
SQLite BLOB
    ↓
Pythonで16bit整数配列へ復元
    ↓
list[int]
    ↓
pywebview
    ↓
JavaScript Array
    ↓
Chart.js
```

となる。

つまり、

> 保存時は容量効率のよいバイナリ形式を使用し、
> 表示するときだけ数値配列へ復元する

という設計ができる。

保存形式と表示形式を同じにする必要はない。

---

# 13. CSVが不要という意味ではない

バイナリ形式は容量効率に優れているが、
CSVには別の利点がある。

CSVは、

- メモ帳で確認できる
- Excelで開ける
- 人間が直接読める
- 他システムへ受け渡ししやすい

という特徴がある。

一方、バイナリデータは専用プログラムを使わなければ
直接内容を確認しにくい。

したがって今回のシステムでは、

```text
日常的な内部保存
    → SQLite BLOB

必要に応じたデータ出力
    → CSVへ変換
```

という使い分けが適している。

これは、

> CSVを保存形式にするのではなく、
> CSVを必要時の「出力形式」として扱う

という考え方である。

---

# 14. バイナリ保存を採用する主な理由

今回のモータ電流データについて、
バイナリ保存を採用する理由は次のように整理できる。

1. **データ容量を約1/3に削減できる**

   5000点の場合、

   ```text
   CSV       約30KB
   バイナリ  約10KB
   ```

   となる。

2. **値の桁数に影響されない**

   16bit整数なら0～65535のどの値でも固定2byteで保存できる。

3. **大量・長期間保存に向いている**

   1日5000波形の場合、

   ```text
   CSV       約150MB/日
   バイナリ  約 50MB/日
   ```

   となり、年間では約36GBの差になる。

4. **PLCの数値データとの相性がよい**

   16bit整数を文字列へ変換せず保存できる。

5. **SQLite BLOBとして1波形を1レコードにまとめやすい**

   5000点を1つのBLOBとして扱えるため、データ管理がシンプルになる。

6. **必要なときだけCSVへ変換できる**

   内部保存は効率を優先し、人間が確認するときだけCSVへ出力する構成にできる。

---

# 15. 設計方針

モータ電流波形の長期保存について、基本方針を次のようにする。

```text
PLC
 ↓
5000点の16bit整数
 ↓
Python
 ↓
バイナリ化
 ↓
SQLite BLOBとして保存
 ↓
必要時
 ├─ Chart.js表示
 └─ CSV出力
```

つまり、

```text
内部保存形式 = バイナリ
表示形式     = 数値配列
外部出力形式 = CSV
```

と役割を分ける。

この構成により、

- 保存容量
- 処理効率
- データ管理
- 人間による確認性

を両立できる。

---

# 16. 結論

5000点のデータについて、
5桁のCSVテキストと16bitバイナリを比較すると、

```text
16bitバイナリ       約10KB
CSV（カンマ区切り） 約30KB
```

となる。

したがって、

> **16bitバイナリはCSVのおよそ1/3の容量で保存できる**

というのが今回の重要な結論である。

1日5000波形を保存した場合には、

```text
16bitバイナリ：約 50MB/日
CSV             ：約150MB/日
```

年間では、

```text
16bitバイナリ：約18GB/年
CSV             ：約55GB/年
```

となり、約36GB/年の差になる。

このため、大量のモータ電流波形を長期間保存する今回の用途では、

> **SQLiteのBLOBへ16bitバイナリ形式で保存し、必要な場合のみCSVへ変換する**

方式を基本設計とする。

CSVは非常に便利な形式だが、大量数値データの内部保存形式としては容量効率が低い。

一方、バイナリ形式は人間が直接読みにくいものの、
大量の数値データをコンパクトに保存する用途には適している。

そのため、

```text
保存はバイナリ
確認・受け渡しはCSV
```

という使い分けが、今回のモータ電流データ管理では合理的である。
