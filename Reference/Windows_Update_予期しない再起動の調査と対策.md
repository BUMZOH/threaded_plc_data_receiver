# Windows Updateによる予期しない再起動の調査と対策

## 1. 今回の目的

設備PCが予期せず再起動したため、次の2点を確認・対策した。

1.  Windowsが再起動した原因を特定する
2.  Windows Updateによる自動インストール・自動再起動を抑制する

今回の調査では、イベントビューアーとローカルグループポリシーを使用した。

------------------------------------------------------------------------

## 2. 再起動原因の調査

### 2.1 イベントビューアーを開く

`Win + R` から次を実行する。

``` text
eventvwr.msc
```

次の場所を確認する。

``` text
イベント ビューアー
└─ Windows ログ
   └─ システム
```

「現在のログをフィルター」で、再起動調査に有用なイベントIDを指定した。

``` text
41,1074,6008,6005,6006
```

### 2.2 主なイベントID

    イベントID 主な意味
  ------------ --------------------------------------------------
            41 正常なシャットダウンを経ずに再起動した可能性
          1074 プロセスやユーザーがシャットダウン・再起動を要求
          6008 予期しないシャットダウン
          6005 Event Logサービス開始。Windows起動の目安
          6006 Event Logサービス停止。正常終了の目安

------------------------------------------------------------------------

## 3. 今回確認されたイベント

2026年9月9日の再起動付近では、主に次のイベントが確認された。

``` text
17:29:08  User32    Event ID 1074
17:31:00  EventLog  Event ID 6006
17:31:43  EventLog  Event ID 6005

17:32:25  User32    Event ID 1074
17:33:02  EventLog  Event ID 6006
17:33:02  EventLog  Event ID 6005

17:33:14  User32    Event ID 1074
17:33:22  EventLog  Event ID 6006
17:33:56  EventLog  Event ID 6005
```

過去の2026年8月24日には Event ID 41 / 6008 も存在したが、
今回の9月9日の再起動原因とは別と判断した。

------------------------------------------------------------------------

## 4. Event ID 1074から分かったこと

Event ID 1074の詳細を確認したところ、再起動を要求したプロセスとして
次のWindowsコンポーネントが確認された。

### MoUsoCoreWorker.exe

``` text
C:\WINDOWS\UUS\AMD64\MoUsoCoreWorker.exe
```

実行ユーザー：

``` text
NT AUTHORITY\SYSTEM
```

理由：

``` text
オペレーティング システム: Service pack (計画済)
```

シャットダウンの種類：

``` text
再起動
```

### TrustedInstaller.exe

``` text
C:\WINDOWS\servicing\TrustedInstaller.exe
```

実行ユーザー：

``` text
NT AUTHORITY\SYSTEM
```

理由：

``` text
オペレーティング システム: アップグレード (計画済)
```

シャットダウンの種類：

``` text
再起動
```

------------------------------------------------------------------------

## 5. 再起動原因の結論

今回の再起動は、停電やクラッシュによる突然の再起動ではなく、

**Windows Update / Windows servicing によって計画的に実行された再起動**

と判断した。

概念的には次の流れだった。

``` text
Windows Update
    ↓
更新処理
    ↓
MoUsoCoreWorker.exe
TrustedInstaller.exe
    ↓
再起動要求
    ↓
Windows再起動
```

`MoUsoCoreWorker.exe` と `TrustedInstaller.exe` は、 Windows
UpdateやWindowsの更新・保守処理で使用されるWindowsのコンポーネントである。

------------------------------------------------------------------------

# 6. 設備PCとしてのWindows Update対策

## 6.1 基本方針

Windows Update自体を完全に無効化するのではなく、

**更新は取得するが、インストールのタイミングは人間が管理する**

という方針にした。

設備PCでは、稼働中にWindows Updateが自動的にインストールされ、
その結果として再起動されることを避けたい。

目標とする運用は次のとおり。

``` text
更新プログラムを検出
        ↓
自動ダウンロード
        ↓
インストール準備完了を通知
        ↓
【担当者が設備の状態を確認】
        ↓
設備を停止できるタイミングでインストール
        ↓
必要に応じて再起動
```

------------------------------------------------------------------------

## 7. ローカルグループポリシーを開く

`Win + R` から次を実行する。

``` text
gpedit.msc
```

今回使用した場所は次のとおり。

``` text
コンピューターの構成
└─ 管理用テンプレート
   └─ Windows コンポーネント
      └─ Windows Update
         └─ エンド ユーザー エクスペリエンスの管理
```

------------------------------------------------------------------------

## 8. 「自動更新を構成する」の設定

「エンド ユーザー エクスペリエンスの管理」にある

``` text
自動更新を構成する
```

を開いた。

設定を次のように変更した。

``` text
有効

自動更新の構成:
3 - 自動ダウンロードしインストールを通知
```

設定後、

``` text
適用
↓
OK
```

で確定した。

一覧画面でも、

``` text
自動更新を構成する    有効
```

になっていることを確認した。

### 「3」の意味

この設定では、更新プログラムは自動的にダウンロードされるが、
インストールの準備ができた段階で通知される。

したがって、今回狙っている運用は、

``` text
Windows Update
    ↓
自動ダウンロード
    ↓
インストール通知
    ↓
担当者が判断
    ↓
手動インストール
    ↓
必要に応じて再起動
```

となる。

------------------------------------------------------------------------

## 9. 「ログオン中は自動再起動しない」ポリシー

「従来のポリシー」にある、

``` text
スケジュールされた自動更新のインストールで、
ログオンしているユーザーがいる場合には
自動的に再起動しない
```

についても「有効」を設定した。

ただし、この設定はレガシーポリシーであり、 適用条件や他のWindows
Updateポリシーとの関係がある。

特に今回採用した `AUOptions = 3` では、
「自動更新を構成する」でインストール自体を通知方式にすることを
主な対策と考える。

したがって、このポリシーだけを

**「どんな場合でも絶対に自動再起動しない保証」**

として扱わない。

------------------------------------------------------------------------

# 10. グループポリシーを即時反映

設定後、コマンドプロンプトから次を実行した。

``` bat
gpupdate /force
```

結果：

``` text
コンピューター ポリシーの更新が正常に完了しました。
ユーザー ポリシーの更新が正常に完了しました。
```

これにより、グループポリシーの更新処理が正常に完了したことを確認した。

------------------------------------------------------------------------

# 11. gpresultによる確認

コンピューター側のグループポリシーを確認する場合は、
**管理者権限のコマンドプロンプト**で次を実行する。

``` bat
gpresult /scope computer /v
```

通常の権限で実行すると、

``` text
エラー: アクセスが拒否されました。
```

となる場合がある。

その場合は「コマンド プロンプト」を
**管理者として実行**してから再度実行する。

------------------------------------------------------------------------

## 12. 一度設定が反映されていなかったケース

最初の確認では `gpresult` に、

``` text
適用されたグループ ポリシー オブジェクト
    N/A
```

さらに、

``` text
ローカル グループ ポリシー
    フィルター: 未適用 (空)
```

と表示された。

グループポリシーエディターを再確認すると、

``` text
自動更新を構成する    未構成
```

になっていた。

つまり、設定画面で「有効」と「3」を選択しただけで、
設定が確定されていなかった。

再度、

``` text
有効
↓
3 - 自動ダウンロードしインストールを通知
↓
適用
↓
OK
```

と設定し、一覧で「有効」と表示されることを確認した。

### 教訓

グループポリシーを変更した場合は、

**設定画面で選択しただけで安心せず、一覧画面の「状態」が
「有効」になったことまで確認する。**

------------------------------------------------------------------------

# 13. レジストリで実際の設定値を確認

グループポリシーを再設定して `gpupdate /force` を実行した後、
次のコマンドでWindows Updateのポリシー値を確認した。

``` bat
reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU"
```

最終的に次の値が確認できた。

``` text
HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU

NoAutoUpdate               REG_DWORD    0x0
AUOptions                  REG_DWORD    0x3
ScheduledInstallDay        REG_DWORD    0x0
ScheduledInstallTime       REG_DWORD    0x3
ScheduledInstallEveryWeek  REG_DWORD    0x1
```

------------------------------------------------------------------------

## 14. 特に重要な値

### AUOptions

``` text
AUOptions    REG_DWORD    0x3
```

`0x3` は10進数の `3` であり、今回設定した

``` text
3 - 自動ダウンロードしインストールを通知
```

がWindowsに反映されていることを確認できた。

### NoAutoUpdate

``` text
NoAutoUpdate    REG_DWORD    0x0
```

Windows Update自体を完全に無効化しているわけではない。

今回の目的はWindows Updateを停止することではなく、

**更新を受け取りつつ、インストールと再起動のタイミングを
設備運用側で管理すること**

である。

------------------------------------------------------------------------

# 15. 最終的な運用イメージ

今回の設定前は、実際に次のような流れで再起動が発生した。

``` text
Windows Update
        ↓
更新をインストール
        ↓
MoUsoCoreWorker.exe
TrustedInstaller.exe
        ↓
再起動要求
        ↓
設備PCが再起動
```

今回の設定後は、通常のWindows Updateについて次の運用を狙う。

``` text
Windows Update
        ↓
更新を検出
        ↓
自動ダウンロード
        ↓
インストールを通知
        ↓
【担当者が設備の稼働状態を確認】
        ↓
設備停止可能な時間にインストール
        ↓
必要に応じて再起動
```

------------------------------------------------------------------------

# 16. 注意点

今回の設定により、

**Windows Updateによる通常の「自動インストール → 再起動」を
抑制する方向の設定**

にはなった。

ただし、

**「今後、どんな条件でもWindowsが絶対に自動再起動しない」**

という保証ではない。

例えば次のような再起動は別問題である。

-   Windowsやドライバーのクラッシュ
-   電源障害
-   ハードウェア障害
-   人間や別ソフトウェアからの再起動要求
-   Windows Updateの別の管理ポリシーや期限設定などによる挙動

したがって設備PCでは、今後もし予期しない再起動が発生した場合も、
イベントビューアーの Event ID 1074、41、6008 などから原因を確認する。

------------------------------------------------------------------------

# 17. 今回の結論

今回の再起動原因は、

**Windows Update / Windows servicingによる計画された再起動**

だった。

対策として、

``` text
自動更新を構成する
    ↓
有効
    ↓
3 - 自動ダウンロードしインストールを通知
```

を設定した。

さらに実際のレジストリで、

``` text
AUOptions = 0x3
```

を確認できた。

したがって今後は、

**更新プログラムは自動ダウンロードし、
設備を停止できるタイミングで人間がインストール・再起動する**

という運用でしばらく様子を見る。

## 19. 今後、再起動が発生したときの確認手順

``` text
予期しない再起動が発生
        ↓
イベントビューアーを開く
        ↓
Windows ログ → システム
        ↓
1074 / 41 / 6008 / 6005 / 6006 を確認
        ↓
1074があれば詳細を確認
        ↓
「どのプロセスが再起動を要求したか」を特定
```

今回のように Event ID 1074 に実行プロセスが記録されていれば、 Windows
Updateなのか、人間の操作なのか、別のソフトウェアなのかを
切り分けるための重要な手掛かりになる。
