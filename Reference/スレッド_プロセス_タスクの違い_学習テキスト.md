
# スレッド・プロセス・タスクの違い
## Pythonの並行処理・並列処理を理解するための基礎

---

# はじめに

Pythonで `ThreadPoolExecutor` や `ProcessPoolExecutor` を学んでいると、

- プロセス
- スレッド
- タスク

という言葉が頻繁に登場します。

この3つは似ているように見えますが、役割はかなり異なります。

最初に一言でまとめると、

- **プロセス**：実行中のプログラムそのもの
- **スレッド**：プロセスの中で実際に処理を進める実行単位
- **タスク**：スレッドやプロセスに「やってもらう仕事」

です。

この違いを理解すると、

```python
ThreadPoolExecutor
ProcessPoolExecutor
submit()
Future
```

などの仕組みも理解しやすくなります。

---

# まず全体像

イメージとしては、会社に例えると分かりやすいです。

```text
会社
│
├─ 作業員A
├─ 作業員B
└─ 作業員C

仕事1
仕事2
仕事3
```

Pythonに置き換えると、

```text
プロセス
│
├─ スレッド1
├─ スレッド2
└─ スレッド3

タスクA
タスクB
タスクC
```

となります。

つまり、

```text
プロセス = 会社
スレッド = 作業員
タスク   = 作業内容
```

と考えると、かなり理解しやすくなります。

---

# 1. プロセスとは

## 定義

**プロセス（Process）とは、OS上で実行されているプログラムの単位です。**

例えばWindowsでPythonプログラムを起動すると、

```text
python.exe
```

というプロセスが作られます。

例えば、

```bash
python app.py
```

を実行すると、

```text
Windows

└─ python.exe
    └─ app.pyを実行中
```

という状態になります。

---

# プロセスは独立したメモリを持つ

プロセスの重要な特徴は、

**それぞれ独立したメモリ空間を持つ**

ことです。

例えば、

```text
Process A

変数
data = 100
```

と、

```text
Process B

変数
data = 200
```

は別物です。

図にすると、

```text
+-----------------------+
| Process A             |
|                       |
| data = 100            |
| 独立したメモリ        |
+-----------------------+

+-----------------------+
| Process B             |
|                       |
| data = 200            |
| 独立したメモリ        |
+-----------------------+
```

となります。

Process AからProcess Bの変数を、そのまま直接触ることはできません。

---

# プロセスのメリット

プロセス同士は独立しているため、

- 他のプロセスの影響を受けにくい
- 片方が異常終了しても他方まで壊れにくい
- CPUコアを使った本当の並列処理ができる
- CPythonのGILをプロセスごとに分離できる

というメリットがあります。

---

# プロセスのデメリット

独立している分、

- メモリ使用量が多い
- 作成コストが比較的大きい
- プロセス間でデータを渡すのが少し面倒
- スレッドより軽量ではない

という特徴もあります。

---

# ProcessPoolExecutorとの関係

Pythonでは、

```python
from concurrent.futures import ProcessPoolExecutor
```

を使うと、複数のプロセスを管理できます。

例えば、

```text
ProcessPoolExecutor

├─ Process1
├─ Process2
└─ Process3
```

のような形です。

CPU負荷の高い処理、

- 画像処理
- FFT
- 大量の数値計算
- CPU中心のデータ処理

などに向いています。

---

# 2. スレッドとは

## 定義

**スレッド（Thread）とは、プロセスの中で実際に処理を実行する単位です。**

1つのプロセスには、最低でも1つのスレッドがあります。

例えば、

```text
python.exe

└─ MainThread
```

です。

`ThreadPoolExecutor` を使うと、さらに複数のスレッドを作れます。

```text
python.exe

├─ MainThread
├─ WorkerThread1
├─ WorkerThread2
└─ WorkerThread3
```

---

# スレッドは同じメモリを共有する

ここがプロセスとの大きな違いです。

同じプロセス内のスレッドは、

**同じメモリ空間を共有します。**

例えば、

```text
Process

共有変数
data = []

├─ Thread1
├─ Thread2
└─ Thread3
```

という状態では、

```text
Thread1
Thread2
Thread3
```

すべてが同じ `data` を参照できます。

---

# スレッドのメリット

- 軽量
- 作成や切り替えが比較的速い
- 同じメモリを簡単に共有できる
- I/O待ちの多い処理に向いている

という特徴があります。

例えば、

- PLC通信
- Socket通信
- HTTP通信
- ファイル読み込み
- ネットワーク待ち

などです。

---

# スレッドのデメリット

メモリを共有するため、

**同じデータを同時に触る危険**

があります。

例えば、

```python
shared_data.append(value)
```

を複数スレッドが同時に実行すると、

処理内容によっては競合が発生する可能性があります。

そのため、

```python
from threading import Lock
```

などを使って、

```python
with lock:
    # 共有データを操作
```

という排他制御が必要になる場合があります。

---

# ThreadPoolExecutorとの関係

```python
from concurrent.futures import ThreadPoolExecutor
```

は、

**複数のスレッドをまとめて管理する仕組み**

です。

例えば、

```text
ThreadPoolExecutor

├─ Thread1
├─ Thread2
└─ Thread3
```

という作業員を用意しておき、

仕事が来たら割り当てます。

---

# 3. タスクとは

## 定義

**タスク（Task）とは、「実行してほしい仕事」です。**

プロセスやスレッドそのものではありません。

例えば、

```python
def receive_motor_data(motor_no):
    ...
```

という関数があるとします。

これを

```python
executor.submit(receive_motor_data, 1)
```

と登録すると、

```text
receive_motor_data(1)
```

という処理が、

**タスクとしてExecutorに登録された**

と考えられます。

---

# タスクは「仕事の依頼」

会社で例えると、

```text
作業員 = スレッド

仕事票 = タスク
```

です。

例えば、

```text
タスクA = モータ1のデータを受信する
タスクB = モータ2のデータを受信する
タスクC = モータ3のデータを受信する
```

という仕事があります。

Executorが、

```text
Thread1 → タスクA
Thread2 → タスクB
Thread3 → タスクC
```

と割り当てます。

---

# タスクとスレッドは1対1ではない

ここは重要です。

例えば、

```python
ThreadPoolExecutor(max_workers=3)
```

としても、

タスクは100個登録できます。

```text
スレッド数 = 3

タスク数 = 100
```

でも問題ありません。

実際には、

```text
Thread1 → Task1 → Task4 → Task7 → ...
Thread2 → Task2 → Task5 → Task8 → ...
Thread3 → Task3 → Task6 → Task9 → ...
```

のように、

1つのスレッドが複数タスクを順番に処理します。

つまり、

> スレッド数とタスク数は別物

です。

---

# ThreadPoolExecutorでの全体像

例えば、

```python
from concurrent.futures import ThreadPoolExecutor


def receive_motor_data(motor_no):
    print(f"Motor {motor_no}")


with ThreadPoolExecutor(max_workers=3) as executor:
    executor.submit(receive_motor_data, 1)
    executor.submit(receive_motor_data, 2)
    executor.submit(receive_motor_data, 3)
```

では、

```text
Pythonプロセス
│
├─ MainThread
│
└─ ThreadPoolExecutor
    │
    ├─ WorkerThread1
    ├─ WorkerThread2
    └─ WorkerThread3

登録されたタスク
├─ receive_motor_data(1)
├─ receive_motor_data(2)
└─ receive_motor_data(3)
```

という関係になります。

Executorがタスクを空いているスレッドへ割り当てます。

---

# 4. プロセス・スレッド・タスクの関係

全体を整理すると、

```text
Windows
│
└─ Pythonプロセス
    │
    ├─ MainThread
    │
    └─ ThreadPoolExecutor
        │
        ├─ WorkerThread1
        ├─ WorkerThread2
        └─ WorkerThread3

タスク
├─ Task A
├─ Task B
├─ Task C
├─ Task D
└─ Task E
```

となります。

タスクは待ち行列に入り、

```text
Task A
Task B
Task C
Task D
Task E
```

空いているスレッドが順番に処理します。

---

# 5. レストランで例える

より直感的に考えてみます。

## プロセス

```text
レストランそのもの
```

です。

別のレストランとは、

- 厨房
- 食材
- スタッフ
- 店舗設備

が基本的に独立しています。

---

## スレッド

```text
料理人
```

です。

同じレストランの中で、

複数の料理人が働いています。

---

## タスク

```text
注文票
```

です。

例えば、

```text
注文1：カレー
注文2：ラーメン
注文3：チャーハン
```

です。

---

## Executor

Executorは、

```text
厨房の責任者
```

のような存在です。

注文票を見て、

```text
料理人A → カレー
料理人B → ラーメン
料理人C → チャーハン
```

と仕事を割り振ります。

つまり、

```text
プロセス = レストラン
スレッド = 料理人
タスク   = 注文
Executor = 責任者
```

です。

# 6. PLCモータ受信アプリで考える

例えばPLCから、

```text
B10.0 → モータ1受信要求
B10.1 → モータ2受信要求
B10.2 → モータ3受信要求
```

を監視しているとします。

Pythonアプリ全体は、

```text
1つのPythonプロセス
```

です。

その中に、

```text
ThreadPoolExecutor

├─ WorkerThread1
├─ WorkerThread2
└─ WorkerThread3
```

があります。

PLCから受信要求が来たら、

```text
Motor1受信処理
Motor2受信処理
Motor3受信処理
```

というタスクをExecutorへ登録します。

例えば、

```python
executor.submit(receive_motor_data, motor_config)
```

です。

このとき、

```text
executor.submit(...)
```

は、

> 「この仕事を空いているスレッドで実行してください」

という依頼です。

---

# 7. タスクを登録した時点ではスレッドを指定しない

ThreadPoolExecutorでは通常、

```python
executor.submit(work)
```

と書くだけです。

「Thread1で実行してください」

とは指定しません。

Executorが自動的に、

```text
Thread1が空いている

↓

Task AをThread1へ渡す
```

のように管理します。

そのため、

プログラマは

```text
どのスレッドが空いているか
```

を自分で管理する必要がありません。

これがThreadPoolExecutorの大きなメリットです。

---

# 8. Futureとの関係

`submit()` の戻り値は、

```python
Future
```

です。

例えば、

```python
future = executor.submit(work)
```

です。

Futureは、

**登録したタスクの将来の結果を表すオブジェクト**

です。

関係は、

```text
タスク
   │
   ▼
Executor
   │
   ▼
スレッドで実行
   │
   ▼
結果
   │
   ▼
Future
```

です。

例えば、

```python
result = future.result()
```

とすると、

タスクの終了を待って結果を受け取れます。

---

# 9. スレッドとタスクを混同しない

初心者が特に混乱しやすいのが、

```text
スレッド = タスク
```

と考えてしまうことです。

これは違います。

例えば、

```python
ThreadPoolExecutor(max_workers=3)
```

では、

```text
スレッドは最大3本
```

です。

しかし、

```python
for i in range(100):
    executor.submit(work, i)
```

なら、

```text
タスクは100個
```

あります。

つまり、

```text
3人の作業員が
100件の仕事を
順番に処理している
```

という状態です。

---

# 10. ProcessPoolExecutorでもタスクという考え方は同じ

タスクはThreadPoolExecutorだけの用語ではありません。

```python
ProcessPoolExecutor
```

でも同じです。

違うのは、

**タスクを実行する担当者がスレッドかプロセスか**

です。

---

## ThreadPoolExecutor

```text
タスク
 ↓
スレッド
```

---

## ProcessPoolExecutor

```text
タスク
 ↓
プロセス
```

---

# 11. 比較表

|項目|プロセス|スレッド|タスク|
|---|---|---|---|
|英語|Process|Thread|Task|
|意味|実行中のプログラム単位|プロセス内の実行単位|実行してほしい仕事|
|OSが管理|はい|はい|通常はExecutorなどが管理|
|独立メモリ|持つ|持たない|メモリそのものではない|
|共有メモリ|基本的に別|同じプロセス内で共有|実行先に依存|
|軽さ|重い|軽い|仕事の定義なので比較対象外|
|例|python.exe|WorkerThread|receive_motor_data(1)|

# 12. GILとの関係

CPythonでは、

同じプロセス内の複数スレッドがPythonコードを実行するとき、

**GIL（Global Interpreter Lock）**

の影響を受けます。

イメージは、

```text
Pythonプロセス

Thread1 ─┐
Thread2 ─┼→ GIL → Pythonコード
Thread3 ─┘
```

です。

一度にPythonコードを実行できるスレッドは基本的に1つです。

そのため、

CPUを大量に使う計算では、

ThreadPoolExecutorでスレッドを増やしても高速化しにくくなります。

---

# 13. それでもThreadPoolExecutorが有効な理由

PLC通信では、

```text
送信

↓

返事待ち

↓

受信
```

のような待ち時間があります。

あるスレッドがPLCの返事を待っている間、

別のスレッドが動けます。

例えば、

```text
Thread1
Motor1へ要求 → PLC待ち
                    ↓
Thread2
              Motor2へ要求 → PLC待ち
                                  ↓
Thread3
                            Motor3へ要求
```

という動きができます。

そのため、

PLC通信のようなI/O中心処理ではThreadPoolExecutorが非常に有効です。

---

# 14. メインスレッドとは

Pythonプログラムを起動すると、

最初に動いているスレッドがあります。

これを、

```text
MainThread
```

と呼びます。

例えば、

```python
print("Hello")
```

だけのプログラムでも、

```text
Pythonプロセス
└─ MainThread
```

があります。

ThreadPoolExecutorを作ると、

```text
Pythonプロセス

├─ MainThread
│
└─ WorkerThread
   WorkerThread
   WorkerThread
```

という構成になります。

---

# 15. 「プロセスの中にスレッドがある」

ここは必ず覚えておきたい関係です。

```text
プロセス
    └─ スレッド
```

です。

逆ではありません。

つまり、

```text
スレッドの中にプロセスがある
```

ではありません。

1つのプロセスが、

```text
1本以上のスレッド
```

を持っています。

---

# 16. 「スレッドの中にタスクがある」わけではない

これも少し注意が必要です。

タスクは、

```text
スレッドの部品
```

ではありません。

タスクはあくまで、

```text
実行してほしい仕事
```

です。

Executorがその仕事を、

```text
空いているスレッド
```

へ割り当てます。

そのため、

```text
タスク
↓
Executor
↓
スレッド
```

という理解が自然です。

---

`ThreadPoolExecutor`

という名前も、ここまで理解すると意味が分かります。

```text
Thread
+

+
Executor
```

です。

---

## Thread

```text

```

---

```text
あらかじめ用意された集まり
```

例えば、

```text

```

の集まりです。

---

## Executor

```text
仕事を実行・管理するもの
```

です。

したがって、

`ThreadPoolExecutor`

とは、

> **複数のスレッドをプールとして持ち、登録されたタスクを割り当てて実行する仕組み**

という意味になります。

---

# まとめ

## プロセス

> **実行中のプログラムそのもの**

- 独立したメモリを持つ
- 比較的重い
- 複数プロセスなら本当の並列処理が可能

---

## スレッド

> **プロセス内部で処理を実行する作業員**

- 同じプロセス内でメモリを共有
- 軽量
- I/O待ち処理に強い
- 共有データを扱う場合はLockが必要になることがある

---

## タスク

> **スレッドやプロセスに実行してもらう仕事**

例えば、

```python
executor.submit(receive_motor_data, 1)
```

なら、

```text
receive_motor_data(1)
```

がタスクです。

---

# 最重要ポイント

次の関係を覚えておけば十分です。

```text
プロセス
│
├─ スレッド
├─ スレッド
└─ スレッド

Executor
│
└─ タスクをスレッドへ割り当てる
```

そして、

```text
プロセス = 工場
スレッド = 作業員
タスク   = 作業指示
Executor = 班長
Future   = 作業結果
```

と覚えると、かなり忘れにくくなります。
