# 設備データ受信アプリ SQLite出力対応 改造仕様書

## 1. 目的

現在の設備データ受信アプリは、PLCから受信した計測データをCSVファイルとして保存している。

今回の改造では、従来のCSV保存機能を残したまま、SQLiteデータベースへの保存にも対応する。

CSVは測定結果をファイルとしてすぐ確認できるため、調査・デバッグ・一時的なデータ取得に便利である。一方、SQLiteは大量の測定データを長期間蓄積し、後から検索・集計・解析する用途に適している。

そのため、コード内の設定によってCSV方式とSQLite方式を切り替えられる構成とする。

------------------------------------------------------------------------

## 2. 現在のアプリ構成

PLCからの計測データ受信は `DataConfig` ごとの設定に基づいて行う。

`DataConfig` は主に以下の情報を保持する。

-   `name`
    -   測定対象名
-   `request_device`
    -   PLCからPCへのデータ受信要求デバイス
-   `completion_device`
    -   PCからPLCへの受信完了通知デバイス
-   `data_start_device`
    -   計測データの読込み開始デバイス
-   `output_directory`
    -   CSVファイルの保存先

PLCからの計測データは32ビット符号付き整数として読み込む。

現在は `save_csv()`
により、測定1回につき1つのCSVファイルを作成している。

------------------------------------------------------------------------

## 3. 保存方式

今回の改造後は、以下の2種類の保存方式に対応する。

### 3.1 CSV方式

従来方式をそのまま残す。

主な用途は以下とする。

-   測定データをすぐに確認したい場合
-   Excelなどで直接データを開きたい場合
-   PLC通信やデータ内容の確認
-   アプリ開発・デバッグ
-   一時的なデータ収集

CSVファイルは従来どおり、`DataConfig.output_directory`
で指定されたフォルダへ保存する。

### 3.2 SQLite方式

PLCから受信した測定データをSQLiteデータベースへ保存する。

主な用途は以下とする。

-   通常運用
-   大量データの長期保存
-   日時や測定対象による検索
-   データ集計
-   将来のMetabaseや解析アプリとの連携
-   AI・統計解析などへの利用

------------------------------------------------------------------------

## 4. 保存方式の切り替え

保存方式はGUIからではなく、Pythonコード内の設定値によって選択する。

設定例：

``` python
SAVE_MODE = "sqlite"  # "csv" または "sqlite"
```

CSV方式を使用する場合：

``` python
SAVE_MODE = "csv"
```

SQLite方式を使用する場合：

``` python
SAVE_MODE = "sqlite"
```

`True / False`
のフラグではなく文字列で指定することで、設定内容をコードから判断しやすくする。

また、将来的に保存方式が増えた場合にも拡張しやすい構成とする。

不正な保存方式が指定された場合は、`ValueError`
を発生させて設定ミスを明確にする。

------------------------------------------------------------------------

## 5. SQLiteデータベース仕様

### 5.1 データベースファイル

データベースファイル名：

``` text
measurement_data.db
```

保存場所：

``` text
data/measurement_data.db
```

Python側では以下のような定数を使用する予定とする。

``` python
DATABASE_PATH = DATA_DIRECTORY / "measurement_data.db"
```

------------------------------------------------------------------------

## 6. テーブル構成

測定対象ごとにテーブルを分割せず、すべての測定データを1つのテーブルへ保存する。

テーブル名：

``` text
measurement_data
```

想定するテーブル定義：

``` sql
CREATE TABLE measurement_data (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    data_name TEXT NOT NULL,
    measured_at TEXT NOT NULL,
    data BLOB NOT NULL
);
```

### 6.1 カラム

#### id

``` text
INTEGER PRIMARY KEY AUTOINCREMENT
```

各測定レコードを一意に識別するID。

アプリ側で値を指定せず、SQLiteによって自動採番する。

#### data_name

``` text
TEXT NOT NULL
```

測定対象名を保存する。

値には、

``` python
DataConfig.name
```

を使用する。

例：

``` text
ToolB_Cross_Torque
SpindleInverter_MotorCurrent
```

#### measured_at

``` text
TEXT NOT NULL
```

データ取得日時を保存する。

形式：

``` text
YYYY-MM-DD HH:MM:SS
```

例：

``` text
2026-08-12 17:20:15
```

Pythonでは以下の形式で生成する。

``` python
datetime.now().strftime("%Y-%m-%d %H:%M:%S")
```

#### data

``` text
BLOB NOT NULL
```

PLCから受信した計測データ本体をバイナリ形式で保存する。

------------------------------------------------------------------------

## 7. BLOBデータ形式

PLCから受信するデータは32ビット符号付き整数の配列である。

Python側では、

``` python
list[int]
```

として受信したデータを、SQLiteへ保存する前にバイナリへ変換する。

変換にはPython標準ライブラリの `struct` を使用する予定とする。

例：

``` python
binary_data = struct.pack(
    f"<{len(values)}i",
    *values,
)
```

ここでは1点を32ビット符号付き整数（4バイト）として保存する。

現在の設定が500点の場合、データ本体のサイズは概算で、

``` text
500点 × 4バイト = 2,000バイト
```

となる。

約2KB/測定であり、大量データの保存にも適したサイズである。

------------------------------------------------------------------------

## 8. テーブルを測定対象ごとに分割しない理由

今回の仕様では、測定対象ごとのテーブル分割は行わない。

すべての測定対象について、

-   測定対象名
-   データ取得日時
-   32ビット整数配列

という同じ構造のデータを保存するためである。

測定対象は `data_name` によって識別する。

この方式には以下のメリットがある。

-   新しい測定対象を追加してもDB構造を変更する必要がない
-   `DATA_CONFIGS` への追加だけで対応しやすい
-   全測定対象を日時で横断検索できる
-   SQLがシンプルになる
-   テーブル数が増えない
-   将来の集計・解析が容易になる

例えば特定の測定対象だけを取得する場合は、

``` sql
SELECT *
FROM measurement_data
WHERE data_name = 'ToolB_Cross_Torque'
ORDER BY measured_at;
```

とする。

特定日の全測定データを取得する場合も、1つのテーブルを検索するだけでよい。

------------------------------------------------------------------------

## 9. インデックス

測定対象と日時による検索を高速化するため、以下の複合インデックスを作成する予定とする。

``` sql
CREATE INDEX idx_measurement_data_name_time
ON measurement_data (data_name, measured_at);
```

これにより、

``` text
測定対象 + 日時
```

を条件とする検索を効率化する。

------------------------------------------------------------------------

## 10. マルチスレッドとSQLite書き込み

現在のアプリでは `ThreadPoolExecutor`
を使用し、複数の測定対象についてデータ受信処理を並行実行できる。

そのため、複数スレッドからSQLiteへの保存要求がほぼ同時に発生する可能性がある。

SQLiteでは複数の読み込み処理は行いやすいが、書き込み処理は基本的に直列化される。

今回のアプリでは構成を必要以上に複雑にしないため、Queueによる専用DB書き込みスレッドは使用せず、SQLiteへの書き込み部分を
`Lock` によって排他制御する方針とする。

イメージ：

``` text
受信スレッド1 ─┐
受信スレッド2 ─┼─→ Lock ─→ SQLite INSERT
受信スレッド3 ─┘
```

PLCからのデータ受信そのものは並行して行い、SQLiteへのINSERTだけを短時間直列化する。

これにより、現在のThreadPoolExecutor構成を維持しながら、安全でシンプルなDB保存を実現する。

------------------------------------------------------------------------

## 11. 保存処理の流れ

改造後の基本的な処理フローは以下とする。

``` text
PLC受信要求
    ↓
PLCから32ビットデータ受信
    ↓
JavaScriptへデータPush
    ↓
SAVE_MODEを確認
    ↓
┌─────────────────┐
│                 │
"csv"          "sqlite"
│                 │
↓                 ↓
save_csv()     save_sqlite()
│                 │
↓                 ↓
CSV保存        SQLite保存
│                 │
└────────┬────────┘
         ↓
PLCへ受信完了通知
```

保存処理が正常に完了してからPLCへ受信完了通知を送る。

------------------------------------------------------------------------

## 12. CSV保存処理

現在の `save_csv()` は基本的にそのまま使用する。

``` python
save_csv(config, values)
```

CSV方式では従来どおり、測定1回につき1ファイルを作成する。

同一秒に複数回保存された場合も既存ファイルを上書きしない現在の処理を維持する。

------------------------------------------------------------------------

## 13. SQLite保存処理

新しく、

``` python
save_sqlite(config, values)
```

を追加する予定とする。

主な処理内容は以下。

1.  受信点数を確認
2.  現在日時を取得
3.  `values` をBLOBへ変換
4.  SQLite書き込み用Lockを取得
5.  `measurement_data.db` へ接続
6.  `measurement_data` テーブルへINSERT
7.  COMMIT
8.  DB接続を閉じる
9.  Lockを解放

保存する値は、

``` text
data_name   = config.name
measured_at = データ取得日時
data        = BLOB化したvalues
```

とする。

------------------------------------------------------------------------

## 14. データフォルダ構成

CSV方式とSQLite方式の両方に対応するため、想定するフォルダ構成は以下とする。

``` text
project/
├─ app.py
├─ index.html
├─ script.js
├─ style.css
└─ data/
   ├─ measurement_data.db
   ├─ data1/
   │  └─ CSVファイル
   ├─ data2/
   │  └─ CSVファイル
   └─ motor3/
      └─ CSVファイル
```

`measurement_data.db` はSQLite方式を使用した場合に利用する。

各CSV保存フォルダはCSV方式を使用するため、`DataConfig.output_directory`
は削除しない。

------------------------------------------------------------------------

## 15. 起動時の処理

SQLite方式を使用する場合は、アプリ起動時にデータベースおよびテーブルを使用可能な状態にする。

初回起動時に `measurement_data.db` が存在しない場合は作成する。

また、`measurement_data`
テーブルや必要なインデックスが存在しない場合は作成する。

既に存在する場合はそのまま使用する。

これにより、手動でSQLiteデータベースを準備しなくてもアプリを起動できる構成とする。

------------------------------------------------------------------------

## 18. 今回の設計方針まとめ

今回の改造では、以下を基本方針とする。

-   CSV保存機能は削除しない
-   SQLite保存機能を新しく追加する
-   保存方式はコード内の `SAVE_MODE` で選択する
-   CSVとSQLiteへの同時保存は行わず、どちらか一方を選択する
-   SQLiteデータベースは `data/measurement_data.db` とする
-   SQLiteは測定対象ごとにテーブルを分割しない
-   `measurement_data` という1つのテーブルへ集約する
-   測定対象は `DataConfig.name` を `data_name` として保存する
-   データ取得日時は `YYYY-MM-DD HH:MM:SS` 形式で保存する
-   計測データ本体は32ビット符号付き整数配列をBLOBとして保存する
-   SQLiteへの書き込みはLockによって排他制御する
-   現在のThreadPoolExecutorによる並行受信構成は維持する
-   CSVはデータ確認・デバッグ用途に活用する
-   SQLiteは通常運用・長期保存・検索・解析用途を主目的とする

この構成により、現在のCSV方式の手軽さを失わず、将来の大量データ蓄積や検索・解析にも対応できる保存方式へ拡張する。
